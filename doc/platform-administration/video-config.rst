Video Configuration
===================

The video frontend can be statically configured by defining :code:`window.Eventyay` before startup.
For example, add the following to the :code:`index.html` you are serving:

.. code-block:: html

	<script>window.Eventyay={"api": {"socket": "wss://sample.demo.Eventyay.org/ws/world/sample/"}, "features": []}</script>

Full configuration
------------------

.. code-block:: js

	{
		"api": {
			"base": "https://sample.demo.Eventyay.org/api/world/sample/",
			"socket": "wss://sample.demo.Eventyay.org/ws/world/sample/",
			"upload": "https://sample.demo.Eventyay.org/storage/upload/"
		},
		"features": [] // enable experimental features,
		"locale": "en", // DEPRECTATED, alias of defaultLocale
		"defaultLocale": "en",
		"locales": ["en", "de", "pt_BR"], // keep this empty to disable user-choosable locale. Order of this array is dropdown order
		"date_locale": "en-ie",
		"timetravelTo": "2020-08-26T06:49:28.975Z", // forces local time to always be this (for schedule demo purposes ONLY)
		// if no token is found in URL hash redirect to given authentication URL.
		// used together with an external server which generates JW tokens based e.g. on user login and password
		"externalAuthUrl": "https://example.com/auth",
		"theme": {
			"logo": {
				"url": "/eventyay-video-logo.svg",
				"fitToWidth": false // optional
			}
			"colors": {
				"primary": '#673ab7', // hightlight color, should be high contrast on white background
				"sidebar": '#180044'
			},
			"streamOfflineImage": "/some-large-image.svg", // image shown instead of "Stream offline"
			// override texts in the ui
			// see video/src/locales for full list of keys
			// DO NOT use this to completely translate the ui
			"textOverwrites": {
				"ProfilePrompt:headline:text": "’ello Guv!"
			},
			"identicons": {
				"style": "identiheart" // the identicon renderer, one of: identiheart, initials
			}
		},
		"videoPlayer": {
			"hls.js": {} // https://github.com/video-dev/hls.js/blob/master/docs/API.md#fine-tuning
		}
	}


Presentation Mode
-----------------

To enter presentation mode, append `/presentation` to a room url.
This shows ONLY the content of the currently pinned question (and updates if anything changes).

You can style presenation mode via custom css:

.. code-block:: css

	// add a background
	#presentation-mode {
		background: url('YOUR_URL_HERE');
		background-size: cover;
		color: A_COLOR_THAT_MATCHES_YOUR_BACKGROUND;
	}

Jitsi Rooms
-----------

Jitsi rooms are available when the :code:`jitsi` feature flag is enabled. Eventyay treats Jitsi as a
dedicated video provider and returns a join configuration only after checking the user's Eventyay room
permissions. The browser then joins the external Jitsi deployment with a JWT generated by Eventyay.

The JWT is issued when the Jitsi iframe is created and expires after 10 minutes. Permission changes in
Eventyay affect newly issued room configurations; users already admitted to the external Jitsi room may keep
their current Jitsi state until they leave or reconnect with a new token.

For reliable attendee and moderator separation, the Jitsi deployment must use JWT authentication. Anonymous
Jitsi rooms are not suitable for this integration because Eventyay cannot enforce Jitsi moderator state after
a user joins without a token.

Architecture
~~~~~~~~~~~~

The integration uses three pieces:

* Eventyay stores one or more Jitsi server records with the public Jitsi URL, JWT app ID, optional key ID,
  shared secret, active state, and optional event restriction.
* Eventyay Jitsi rooms store only room-level preferences such as preferred server URL and initial mute
  settings. JWT credentials are never stored in a room configuration.
* The Jitsi deployment validates Eventyay-issued JWTs and loads the Eventyay Prosody modules from
  :code:`deployment/jitsi/prosody-plugins-custom/`.

Eventyay generates the final Jitsi conference name from stable Eventyay event and room IDs. Room display-name
changes and translations do not change the external Jitsi conference.

Jitsi Server Fields
~~~~~~~~~~~~~~~~~~~

Configure Jitsi servers in the global video admin area.

* :code:`url`: Public HTTPS Jitsi Meet URL, for example :code:`https://meet.example.org`.
* :code:`app_id`: JWT issuer/application ID. This must match :code:`JWT_APP_ID` and
  :code:`JWT_ACCEPTED_ISSUERS` on the Jitsi deployment.
* :code:`key_id`: Optional JWT :code:`kid` header value. Leave empty for shared-secret HS256 testing.
* :code:`app_secret`: JWT shared secret. This must match :code:`JWT_APP_SECRET` on the Jitsi deployment.
* :code:`event_exclusive`: Optional event restriction for the server.

Jitsi Room Fields
~~~~~~~~~~~~~~~~~

Room admins can configure:

* :code:`prefer_server`: Optional preferred Jitsi server URL. Eventyay still only selects an active server
  that is available for the event.
* :code:`start_with_audio_muted`: Ask Jitsi to join with audio muted.
* :code:`start_with_video_muted`: Ask Jitsi to join with video muted.

Azure VM Test Deployment
~~~~~~~~~~~~~~~~~~~~~~~~

The following runbook installs docker-jitsi-meet on an Ubuntu Azure VM with a public DNS name such as
:code:`meet.example.org`. Use at least 2 vCPUs and 4 GiB RAM for multi-user browser testing.

1. Configure Azure networking.

   Point the DNS name to the VM public IP. In the Azure Network Security Group attached to the VM NIC or
   subnet, allow:

   * :code:`80/tcp` for certificate HTTP validation and redirect handling.
   * :code:`443/tcp` for the Jitsi web UI.
   * :code:`10000/udp` for Jitsi Videobridge media.

   Keep :code:`22/tcp` restricted to trusted source IPs if possible.

2. Clean old Docker state on the VM.

   Run this only on a dedicated test VM where removing old containers, images, networks, and volumes is
   acceptable:

   .. code-block:: bash

      docker compose down --remove-orphans --volumes || true
      docker ps -aq | xargs -r docker rm -f
      docker images -aq | xargs -r docker rmi -f
      docker volume ls -q | xargs -r docker volume rm
      docker network prune -f
      docker builder prune -af

3. Install Docker and required tools.

   .. code-block:: bash

      sudo apt-get update
      sudo apt-get install -y ca-certificates curl gnupg unzip wget certbot
      curl -fsSL https://get.docker.com | sudo sh
      sudo usermod -aG docker "$USER"

   Log out and back in after adding the user to the :code:`docker` group.

4. Download docker-jitsi-meet.

   Use the latest official release package:

   .. code-block:: bash

      wget -O docker-jitsi-meet.zip "$(wget -q -O - https://api.github.com/repos/jitsi/docker-jitsi-meet/releases/latest | grep zipball_url | cut -d\" -f4)"
      unzip docker-jitsi-meet.zip
      cd jitsi-docker-jitsi-meet-*
      cp env.example .env
      ./gen-passwords.sh

5. Create the docker-jitsi-meet configuration directories.

   Current docker-jitsi-meet releases run with a read-only root filesystem and need writable storage and
   temporary directories:

   .. code-block:: bash

      mkdir -p ~/.jitsi-meet-cfg/{web,prosody/config,prosody/prosody-plugins-custom,jicofo,jvb,jigasi,jibri,transcriber}
      mkdir -p ~/.jitsi-meet-cfg/storage/{jibri,prosody,transcripts,web}
      mkdir -p ~/.jitsi-meet-cfg/tmp/{web-crontabs,web-load-test}
      chmod 777 ~/.jitsi-meet-cfg/storage/{jibri,prosody,transcripts,web}
      chmod 777 ~/.jitsi-meet-cfg/tmp/{web-crontabs,web-load-test}

6. Issue a trusted certificate on the host.

   The docker-jitsi-meet built-in ACME flow can fail in some environments while the web container is still
   starting. For predictable Azure testing, issue the certificate with host certbot first:

   .. code-block:: bash

      sudo systemctl stop nginx apache2 haproxy || true
      sudo certbot certonly --standalone \
        -d meet.example.org \
        --email admin@example.org \
        --agree-tos \
        --non-interactive

   Copy the certificate into the docker-jitsi-meet web config directory:

   .. code-block:: bash

      mkdir -p ~/.jitsi-meet-cfg/web/keys
      sudo cp /etc/letsencrypt/live/meet.example.org/fullchain.pem ~/.jitsi-meet-cfg/web/keys/cert.crt
      sudo cp /etc/letsencrypt/live/meet.example.org/privkey.pem ~/.jitsi-meet-cfg/web/keys/cert.key
      sudo chown -R "$USER:$USER" ~/.jitsi-meet-cfg/web/keys
      chmod 600 ~/.jitsi-meet-cfg/web/keys/cert.key

7. Configure docker-jitsi-meet.

   Edit :code:`.env` and set the public URL, host-provided certificate mode, JWT authentication, and the
   Eventyay Prosody module:

   .. code-block:: text

      HTTP_PORT=80
      HTTPS_PORT=443
      PUBLIC_URL=https://meet.example.org
      ENABLE_HTTP_REDIRECT=1

      ENABLE_LETSENCRYPT=0

      ENABLE_AUTH=1
      ENABLE_GUESTS=0
      AUTH_TYPE=jwt
      JWT_APP_ID=eventyay
      JWT_APP_SECRET=<shared-secret-used-in-eventyay-admin>
      JWT_ACCEPTED_ISSUERS=eventyay
      JWT_ACCEPTED_AUDIENCES=jitsi
      JWT_ALLOW_EMPTY=0

      XMPP_MUC_MODULES=eventyay_token_affiliation_force

   If users can join but media does not flow, also set:

   .. code-block:: text

      JVB_ADVERTISE_IPS=<azure-vm-public-ip>

8. Add reboot-safe restart policies.

   Create :code:`compose.override.yml` next to docker-jitsi-meet's compose file:

   .. code-block:: yaml

      services:
        web:
          restart: unless-stopped
        prosody:
          restart: unless-stopped
        jicofo:
          restart: unless-stopped
        jvb:
          restart: unless-stopped

   If extra services such as :code:`jigasi`, :code:`jibri`, or :code:`transcriber` are enabled, add the same
   restart policy for them.

9. Copy the Eventyay Prosody modules.

   From the Eventyay repository on the local development machine:

   .. code-block:: bash

      scp deployment/jitsi/prosody-plugins-custom/*.lua <vm-user>@meet.example.org:/tmp/

   On the VM:

   .. code-block:: bash

      cp /tmp/mod_*.lua ~/.jitsi-meet-cfg/prosody/prosody-plugins-custom/
      ls -l ~/.jitsi-meet-cfg/prosody/prosody-plugins-custom/

   The directory must contain:

   * :code:`mod_eventyay_token_affiliation_force.lua`
   * :code:`mod_end_conference.lua`

   Only :code:`eventyay_token_affiliation_force` is listed in :code:`XMPP_MUC_MODULES`. The guarded
   :code:`end_conference` module is loaded by Jitsi's end-conference component from the same custom plugin
   directory. Loading :code:`end_conference` through :code:`XMPP_MUC_MODULES` causes a
   :code:`No muc_component specified` Prosody error.

10. Copy the Eventyay Jitsi web customizations.

    These files remove Jitsi branding from the served web app and hide disabled Jitsi features.
    The iframe overrides sent by Eventyay are still kept, but the server-side files are required for Jitsi
    versions that do not honor branding and disabled-feature changes from client-side overrides.

    From the Eventyay repository on the local development machine:

    .. code-block:: bash

       scp deployment/jitsi/web/custom-*.js <vm-user>@meet.example.org:/tmp/

    On the VM:

    .. code-block:: bash

       cp /tmp/custom-config.js ~/.jitsi-meet-cfg/web/custom-config.js
       cp /tmp/custom-interface_config.js ~/.jitsi-meet-cfg/web/custom-interface_config.js
       ls -l ~/.jitsi-meet-cfg/web/custom-*.js

11. Start Jitsi.

    .. code-block:: bash

       docker compose config >/dev/null
       docker compose up -d
       docker compose ps

    The :code:`web`, :code:`prosody`, :code:`jicofo`, and :code:`jvb` services should all be :code:`Up`.

12. Verify the deployment.

    Check HTTPS:

    .. code-block:: bash

       curl -I https://meet.example.org

    Check restart policies:

    .. code-block:: bash

       docker inspect -f '{{.Name}} {{.HostConfig.RestartPolicy.Name}}' \
         <compose-project>-web-1 \
         <compose-project>-prosody-1 \
         <compose-project>-jicofo-1 \
         <compose-project>-jvb-1

    Each container should report :code:`unless-stopped`.

    Check the Prosody modules:

    .. code-block:: bash

       docker compose logs --tail=200 prosody | grep -E 'Eventyay|end_conference|eventyay'

    Expected log lines include:

    .. code-block:: text

       Starting Eventyay guarded end_conference for muc.meet.jitsi

    After an attendee joins through Eventyay, Prosody should log a forced member affiliation similar to:

    .. code-block:: text

       eventyay forced affiliation=member role=participant

13. Configure Eventyay.

    Start Eventyay locally from the branch and apply migrations:

    .. code-block:: bash

       cp deployment/env.dev.sample .env.dev
       docker compose up -d --build
       docker compose exec web python manage.py migrate
       docker compose exec web python manage.py create_admin_user

    In the Eventyay global video admin area, create a Jitsi server:

    * :code:`URL`: :code:`https://meet.example.org`
    * :code:`App ID`: :code:`eventyay`
    * :code:`App secret`: the same value as :code:`JWT_APP_SECRET`
    * :code:`Key ID`: empty for HS256 shared-secret testing
    * :code:`Active`: checked
    * :code:`Event exclusive`: optional

    Enable the :code:`jitsi` feature flag for the event, create a Jitsi room, and join through Eventyay.
    Directly creating a room on the Jitsi homepage may fail because anonymous access is disabled; this is
    expected for JWT-secured testing.

Manual Test Checklist
~~~~~~~~~~~~~~~~~~~~~

* Join as a user with :code:`room:jitsi.join` and verify the Jitsi room opens.
* Join as a user with :code:`room:jitsi.moderate` and verify the user receives moderator behavior.
* Confirm the Jitsi watermark/logo is not visible in the embedded room.
* Confirm the Jitsi room UI uses the default Jitsi palette without Jitsi branding.
* Join as a user without :code:`room:jitsi.join` and verify Eventyay denies the room configuration request.
* Join as an attendee and verify Prosody logs show forced member affiliation.
* Confirm attendees cannot grant themselves moderator status or end the conference for everyone.
* Confirm the room configuration returned to the frontend does not contain :code:`app_secret`,
  :code:`app_id`, :code:`key_id`, or other server-side JWT credentials.

Certificate Renewal
~~~~~~~~~~~~~~~~~~~

The host certbot certificate should be renewed outside the Jitsi containers. Verify renewal with:

.. code-block:: bash

   sudo certbot renew --dry-run

After renewal, copy the renewed files into :code:`~/.jitsi-meet-cfg/web/keys/` and restart the web container:

.. code-block:: bash

   sudo cp /etc/letsencrypt/live/meet.example.org/fullchain.pem ~/.jitsi-meet-cfg/web/keys/cert.crt
   sudo cp /etc/letsencrypt/live/meet.example.org/privkey.pem ~/.jitsi-meet-cfg/web/keys/cert.key
   sudo chown -R "$USER:$USER" ~/.jitsi-meet-cfg/web/keys
   chmod 600 ~/.jitsi-meet-cfg/web/keys/cert.key
   docker compose restart web

Troubleshooting
~~~~~~~~~~~~~~~

If docker-jitsi-meet cannot bind ports :code:`80` or :code:`443`, stop any host service using them:

.. code-block:: bash

   sudo ss -ltnp 'sport = :80'
   sudo ss -ltnp 'sport = :443'
   sudo systemctl stop nginx apache2 haproxy || true
   sudo systemctl disable nginx apache2 haproxy || true

If certificate issuance fails, confirm that DNS resolves to the VM and port :code:`80` is reachable from
outside the VM:

.. code-block:: bash

   curl -4s ifconfig.me
   getent ahostsv4 meet.example.org | head -1

From another machine:

.. code-block:: bash

   curl -v http://meet.example.org

If media does not flow after users join, verify that Azure allows :code:`10000/udp` inbound and set
:code:`JVB_ADVERTISE_IPS` to the VM public IP.
